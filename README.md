# Elevator Controller

מימוש הדרגתי של תרגיל בקר המעלית. בשלב הנוכחי ממומשים מודל הנתונים,
אוסף הבקשות הממתינות ומדיניות התזמון. החיבור לחומרה ושני חוטי העבודה
הם השלב הבא; כרגע אין כאן בקר חומרה פעיל.

## הרצה

נדרשת Python 3.10 ומעלה. הקוד משתמש בספרייה הסטנדרטית בלבד.

```powershell
py -m unittest discover -s tests -v
py -m elevator_controller
```

הפקודה השנייה מדגימה התחייבות לאיסוף בקומה 8 ובקשה חדשה לרדת לקומה 1.
ההדגמה מקדמת אירועים ידנית ואינה מפעילה חומרה או חוטים.

## מבנה

| קובץ | אחריות |
| --- | --- |
| `elevator_controller/models.py` | בקשות, מצבי מעלית, עצירה ומסלול |
| `elevator_controller/requests.py` | איחוד בקשות כפולות והשלמת שירות |
| `elevator_controller/scheduler.py` | בחירת מסלול והצעת עצירות ביניים |
| `tests/test_scheduler.py` | בדיקות התנהגות וגבולות |

`HallRequest` ו-`CabinRequest` הן מחלקות נתונים. `Elevator` הוא צילום מצב
בלתי ניתן לשינוי; בעתיד הבקר יחליף אותו בעקבות אירועי חומרה. `Route` גם
הוא בלתי ניתן לשינוי, כך שהצעה לשינוי מסלול לא משנה את המסלול הפעיל.

## מדיניות התזמון

1. מתכננים מסלול חדש רק כשאין מסלול פעיל או התחייבות שירות אחרת,
   המעלית עומדת, הדלתות סגורות ואין תקלה.
2. קריאה חיצונית שעברה את סף ההמתנה מקבלת עדיפות; מבין כאלה נבחרת הוותיקה.
3. אחרת, בקשה פנימית קרובה קובעת את הכיוון. המסלול כולל את כל היעדים
   הפנימיים הידועים בכיוון הזה, עד הרחוק ביותר. בשוויון מרחק מעדיפים
   את הכיוון הקודם; בהיעדרו, את הקומה הנמוכה.
4. אם אין בקשות פנימיות, נבחרת הקריאה החיצונית הוותיקה ביותר כיעד איסוף.
5. בדרך מוסיפים יעדים פנימיים וקריאות חיצוניות שמתאימות לכיוון, בלי לעבור
   את קומת הסיום. בעצירת האיסוף האחרונה כיוון השירות הוא כיוון בקשת הנוסע,
   גם אם המעלית הגיעה מהכיוון ההפוך.
6. בקשה חדשה אינה מבטלת עצירה קיימת, הופכת את הכיוון או מאריכה את המסלול.
   בקשות שאינן מתאימות נשמרות למסלול הבא.
7. הגעה או אישור פקודה אינם השלמת בקשה. מסירים בקשות רק אחרי פתיחת
   דלתות, ובקריאות חיצוניות מסירים רק את כיוון השירות.

רק קריאה חיצונית שנבחרה כיעד איסוף, או שולבה כעצירה, היא התחייבות.
קריאה שממתינה בקומה 8 אינה אוטומטית חלק מכל מסלול שעובר בקומה 7.

סף ההמתנה הוא פרמטר `max_hall_wait`. ברירת המחדל של 60 שניות היא דוגמה
ניתנת לשינוי, לא דרישה במסמך. הזמן נמדד באמצעות שעון מונוטוני; בבדיקות
מעבירים זמנים מפורשים. הסף מבטיח קדימות בתכנון הבא, לא איסוף תוך 60 שניות:
צריך קודם להשלים את המסלול והשירות הפעילים, וייתכנו קריאות ותיקות יותר.

המסלול המוגבל הוא בחירה לטובת הוגנות ופשטות. הוא יכול לדחות אפילו יעד
פנימי חדש שנמצא מעבר לקצה המסלול. זו אינה טענה לאופטימום של זמני הנסיעה.

## החוזה לשלב החיבור לחומרה

- חוט האזנה יקרא אירועים ויעביר אותם אל `queue.Queue`.
- חוט בקרה יחיד יחזיק ב-`PendingRequests`, במצב המעלית ובמסלול הפעיל.
  אוסף הבקשות אינו תור האירועים ואינו נועד לכתיבה מכמה חוטים.
- פקודות תנועה ודלתות יחזרו מיד; השלמה תדווח באירוע נפרד.
- כאשר `propose_route_update` משנה את היעד הבא בזמן נסיעה, הבקר יבקש
  אישור מהחומרה לפני החלפת המסלול הפעיל. בדחייה שומרים את המסלול המקורי
  ואת כל הבקשות. החומרה אחראית לקבוע אם נותר מספיק מרחק לעצירה.
- בזמן תנועה `current_floor` היא הקומה האחרונה שדווחה. אין מוסיפים עצירה
  חדשה בקומה שכבר דווחה כקומה שעברנו.
- אירוע פתיחת דלתות יגרום לקריאה ל-`mark_served`, ורק לאחריה ל-
  `Route.after_servicing`. בזמן עצירה שומרים את כיוון השירות גם אם המסלול
  כבר הסתיים; לחיצה חדשה שמתאימה לעצירה עם דלתות פתוחות תטופל באותו שירות.
- הפעלת נסיעה תמתין לאירוע סגירת דלתות. זמן ההמתנה לנוסעים ינוהל באמצעות
  מועד סיום ו-timeout בתור, ולא באמצעות `sleep` בחוט הבקרה.

הבדיקות בשלב הזה מאמתות את מדיניות התזמון, לא תזמון חוטים או חומרה אמיתית.
